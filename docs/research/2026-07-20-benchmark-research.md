# 국내 교과서 기반 AI 벤치마크 조사 보고서

- 조사일: 2026-07-20
- 목적: EduBench 구현 전에 기존 벤치마크의 운영 구조, 문항 형식, 채점 방식, 공정성 통제, 결과 보고 방식을 검토하고 국내 교과서 기반 교육 AI 평가에 맞는 설계를 도출한다.
- 범위: 한국어·K-12 교육·교과과정 정합성·RAG 근거성·자유서술형 평가·LLM 심판 편향·재현 가능한 실행 프레임워크
- 조사 방식: 학술 논문, 공식 프로젝트 문서, 공식 저장소를 우선했다. 검색 결과를 그대로 채택하지 않고 원문 초록·방법론·공식 구현 문서를 교차 확인했다.
- 주의: 2026년 논문 일부는 아직 동료평가가 완료되지 않은 arXiv 사전 공개본이다. 이 문서에서는 설계 아이디어의 근거로 사용하되 확립된 표준으로 표현하지 않는다.

## 1. 요약 결론

EduBench는 일반 지식시험을 복제해서는 목적을 달성할 수 없다. 국내 교과서 기반 학습 서비스에 필요한 능력은 다음처럼 분리해서 측정해야 한다.

1. 교과서 핵심 개념의 정확한 이해
2. 개념 적용과 문제 해결
3. 선수 개념·인접 개념·단원 간 연결
4. 학년 수준에 맞춘 설명
5. 오개념과 잘못된 주장 교정
6. 교과서 근거 충실도와 범위 이탈 억제
7. 근거가 없을 때 추측하지 않는 능력
8. 한국어 설명의 명료성
9. 비용, 지연시간, 실패율 같은 운영 품질

정답률 하나로 합치면 어떤 모델이 교육 서비스에 적합한지 설명하기 어렵다. HELM과 OpenLearnLM의 핵심 교훈처럼 다축 결과를 기본으로 하고, 종합점수는 보조 지표로만 제공해야 한다.

권장 평가 구조는 다음과 같다.

- 500개 문항을 고정된 데이터셋 버전으로 관리한다.
- 객관식, 단답형, 구성형 서술 문항을 혼합한다.
- 각 문항에는 원자적 채점 항목, 허용 답안, 금지 오개념, 교과서 근거 청크를 저장한다.
- 자동 채점과 LLM 채점을 사용하되 사람 검수 표본으로 보정한다.
- 모델 이름을 숨긴 절대평가를 기본으로 하고, 직접 비교는 부차 분석으로 둔다.
- 모든 모델에 같은 의미의 프롬프트, 같은 응답 길이 제약, 같은 문항 순서를 사용하되 실행 순서는 모델별로 교차·무작위화한다.
- 결과에는 평균뿐 아니라 95% 신뢰구간, 문항별 차이, 실패 사례, 표본 수를 표시한다.

|---|---|---|---|---|
| KMMLU | 한국 시험에서 수집한 45개 분야 한국어 지식 평가 | 35,030개 객관식 | 번역 문항보다 국내 원문 문항이 한국 언어·문화 특성을 더 잘 반영한다는 근거 | 전문가 수준 시험 중심이며 교과서 근거·학생 수준 설명을 평가하지 않음 |

| K12-KGraph / K12-Bench | 공식 교과서에서 교과과정 지식 그래프 구성 | Ground, Prereq, Neighbor, Evidence, Locate 다중선택 | 단원·선수 개념·근거 위치·교과과정 순서를 직접 평가 | 중국 교과서 기반이며 2026년 사전 공개 연구 |
| CogBench | 학생 인지 수준에 맞는 풀이·설명 평가 | 수학 2.1K 문항, 수준별 복수 정답 | 정답 여부와 별도로 학년·인지 수준 정합성을 측정 | 수학 중심이며 국내 교과과정 적용을 새로 설계해야 함 |
| Dr.Academy | 교육적 질문 생성 능력을 Bloom 계열 분류로 평가 | 일반·단일 과목·융합 질문 생성 | 생성 문항의 관련성, 범위, 대표성, 일관성을 검수 지표로 활용 | 답변 모델의 성능 벤치마크가 아니라 문항 생성 평가 |
| SciEx | 실제 시험형 자유서술 응답을 전문가와 LLM이 채점 | 자유서술·멀티모달·난이도 혼합 | 자유서술형은 상세 루브릭과 전문가 표본 채점이 필요 | 대학 컴퓨터과학 시험 중심 |
| HELM | scenario/adaptation/metric 분리, 재현성과 투명성 강조 | 다수 시나리오와 다중 지표 | 문항, 프롬프트 적용 방식, 모델 설정, 지표를 버전별로 분리·기록 | EduBench의 도메인 데이터와 루브릭은 별도 구축 필요 |
| lm-evaluation-harness | 모델 어댑터와 태스크 정의를 분리 | YAML 태스크, 공통 모델 인터페이스, 캐시 | 제공사별 API를 공통 어댑터로 정규화하고 태스크 정의를 버전 관리 | 자유서술 채점·교과서 RAG 검수 UI는 직접 구현해야 함 |
| Inspect AI | dataset + solver + scorer + eval log | 문자열·모델·사용자 정의 채점 | 데이터, 실행, 채점, 로그의 책임 분리 | 완성된 데이터 운영 UI가 아니라 평가 프레임워크 |

## 3. 기존 시스템은 어떻게 작동하는가

### 3.1 공통 구조

성숙한 벤치마크 프레임워크는 대부분 다음 네 계층을 분리한다.

1. Dataset/Scenario: 무엇을 물을지 정의한다.
2. Adaptation/Solver: 모델에 어떤 프롬프트 형식과 설정으로 전달할지 정의한다.
3. Model adapter: 제공사별 API 차이를 공통 요청·응답으로 바꾼다.
4. Scorer/Metric: 결과를 어떤 규칙과 루브릭으로 평가할지 정의한다.

EduBench도 같은 경계를 따라야 한다. 문항이 바뀐 것과 프롬프트가 바뀐 것, 모델 버전이 바뀐 것, 채점 규칙이 바뀐 것을 하나의 버전으로 섞으면 재현할 수 없다.

### 3.2 태스크 정의와 실행을 분리하는 이유

lm-evaluation-harness는 공유 가능한 YAML 태스크 설정과 코드 커밋 해시로 평가 조건을 재현하도록 설계한다. 채팅 템플릿과 시스템 프롬프트도 결과에 보관한다. EduBench에서는 이를 다음 객체로 옮긴다.

- `dataset_version`: 승인된 500개 문항 스냅샷
- `prompt_profile_version`: 공통 시스템 프롬프트와 문항 렌더링 규칙
- `model_config_version`: 모델 ID, 엔드포인트, 파라미터
- `scoring_profile_version`: 문항 유형별 채점 규칙과 평가 모델
- `run`: 위 네 버전의 불변 조합

### 3.3 중단·재개와 캐시

기존 프레임워크는 요청 캐시나 평가 로그를 남긴다. EduBench에서는 응답 캐시를 단순 성능 최적화가 아니라 재현성 데이터로 취급해야 한다.

- 각 호출은 `run_id + question_id + model_config_id + attempt`로 식별한다.
- 성공 응답은 다시 호출하지 않는다.
- 실패 응답만 새 attempt로 재시도한다.
- 원본 요청, 원본 응답, HTTP 상태, 제공사 요청 ID, 시작·종료 시각, 토큰 사용량을 보관한다.
- 프롬프트나 모델 설정이 바뀌면 같은 캐시 키를 사용하지 않는다.

## 4. 문항 형식 설계

### 4.1 권장 500문항 능력 분포

초기 기획의 비율은 유지하되 내부 하위유형을 더 명확히 한다.

| 주 능력 | 문항 수 | 필수 하위유형 |
|---|---:|---|
| 교과서 핵심 개념 이해 | 150 | 정의, 개념 구분, 원리 설명, 교과서 용어 사용 |
| 개념 적용 및 문제풀이 | 120 | 계산, 사례 적용, 조건 변경, 풀이 오류 탐지 |
| 여러 단원 연결 추론 | 80 | 선수 개념, 인접 개념, 원인-결과, 복수 근거 통합 |
| 학생 수준별 설명 | 80 | 학년 어휘, 단계 수, 선수지식 제한, 비유의 적절성 |
| 오개념·잘못된 주장 교정 | 70 | 오개념 식별, 교정 근거, 범위 밖 주장 구분, 근거 부족 시 유보 |
| 합계 | 500 |  |

이 다섯 범주는 상호 배타적인 주 분류다. `근거 유형`, `인지 수준`, `문항 형식`, `학년`, `과목`, `난이도`는 별도의 교차 태그로 저장한다.

### 4.2 권장 응답 형식 분포

근거 자료 제작이 목적이므로 객관식에 치우치지 않는다.

| 응답 형식 | 권장 수 | 역할 |
|---|---:|---|
| 객관식 | 100 | 정답률과 기본 지식의 안정적 비교 |
| 단답형 | 100 | 용어·수치·짧은 결론의 정확성 측정 |
| 구조화 서술형 | 200 | 핵심 개념, 근거, 완결성의 원자적 루브릭 평가 |
| 학생 설명형 | 60 | 학년 수준, 명료성, 불필요한 고급 개념 사용 측정 |
| 교정·범위 판단형 | 40 | 오개념, 환각, 교과서 외삽, 답변 유보 능력 측정 |
| 합계 | 500 |  |

`학생 설명형`과 `교정형`은 기술적으로 서술 응답이지만 분석 화면에서 독립 형식으로 노출한다.

### 4.3 Bloom/인지 수준

각 문항에는 다음 중 하나의 주 인지 수준을 저장한다.

- 기억: 정의·용어 재현
- 이해: 관계와 원리를 자기 언어로 설명
- 적용: 새로운 사례나 수치에 개념 사용
- 분석: 조건, 오류, 원인, 복수 개념 관계 분해
- 평가: 주장·풀이·근거의 타당성 판단
- 창안은 기본 벤치마크에서 제외: 정답 범위가 지나치게 넓어 500문항 규모에서 신뢰도 확보가 어렵다.

OpenLearnLM과 Dr.Academy는 Bloom 계열 분류의 실용성을 보여주지만, 난이도를 Bloom 수준과 동일시해서는 안 된다. 같은 `적용` 문항도 계산 복잡도와 필요한 선수 개념에 따라 난이도가 달라진다.

### 4.4 교과과정 구조 태스크

K12-KGraph의 아이디어를 국내 교과서 메타데이터에 맞게 경량 적용한다.

- Ground: 이 개념이 어느 학년·단원 범위에 속하는가
- Prerequisite: 답변에 필요한 선수 개념은 무엇인가
- Neighbor: 같은 단원 또는 인접 단원의 관련 개념은 무엇인가
- Evidence: 어느 근거 문장이 답을 지지하는가
- Locate: 교과서의 파일·단원·페이지·청크 위치는 어디인가

질문 생성 시 이 구조를 사용하면 단순히 유사한 문단을 다시 묻는 문항을 줄일 수 있다.

### 4.5 객관식 설계 규칙

E-EVAL은 정답 선택지 A/B/C/D 분포를 균형 있게 조정해 선택지 위치 편향을 줄였다. EduBench도 다음 규칙을 적용한다.

- 정답 위치를 데이터셋 전체와 주요 층별로 균등 배치한다.
- 모든 모델에 동일한 선택지 순서를 사용한다.
- 선택지 길이·문체만으로 정답을 추측할 수 없도록 검수한다.
- 복수정답 문항은 별도 유형으로 명시하고 부분점수 규칙을 고정한다.
- `정답 문자만`과 `근거 포함 답변`을 혼합하지 않는다. 목적에 따라 문항 스키마에서 출력 형식을 고정한다.

## 5. 교과서 근거 제공 방식: 핵심 설계 쟁점

질문만 주는 폐쇄형 평가와 근거 청크를 함께 주는 개방형 평가는 서로 다른 능력을 측정한다.

### 폐쇄형(closed-book)

- 측정 대상: 모델이 이미 학습한 국내 교육과정·한국어 지식
- 장점: 모델 자체의 내재 지식을 비교하기 쉬움
- 한계: 실제 교과서 RAG 학습 서비스의 작동 방식을 직접 반영하지 못함

### 근거 제공형(grounded/open-book)

- 측정 대상: 제공된 교과서 문맥을 읽고 정확히 인용·통합·제한하는 능력
- 장점: 실제 서비스에서 필요한 근거 활용, 환각 억제, 범위 준수를 직접 측정
- 한계: 검색 품질이 모델 답변 품질에 섞일 수 있음

### 권장안

단일 점수로 섞지 말고 한 데이터셋 안에서 평가 모드를 명시한다.

- 주 평가: 승인된 근거 청크를 모든 모델에 동일하게 제공하는 `grounded` 문항
- 보조 진단: 질문만 제공하는 `closed_book` 문항
- 근거 없음 또는 충돌을 의도한 `insufficient_evidence` 문항을 소수 포함

검색기가 실시간으로 각 모델에 서로 다른 청크를 제공하면 모델 비교가 아니라 모델+검색기 조합 비교가 된다. 따라서 본 벤치마크의 주 평가에서는 검수자가 확정한 동일 근거 패킷을 사용해야 한다. 검색 품질 자체는 문항 생성 파이프라인의 별도 RAG 품질 지표로 평가한다.

## 6. 문항 생성 파이프라인 평가

Dr.Academy는 생성된 교육 질문을 관련성, 범위, 대표성, 일관성으로 평가한다. ARES는 합성 질의·정답에 강한 음성과 약한 음성을 함께 만들어 평가기를 학습한다. 이를 EduBench에 적용하면 다음 품질 게이트가 적합하다.

1. 관련성: 선택 과목·학년·단원·목적과 직접 관련되는가
2. 근거 충분성: 정답의 각 핵심 주장에 교과서 근거가 있는가
3. 범위 적합성: 교육과정 밖 지식을 정답의 필수조건으로 요구하지 않는가
4. 대표성: 일부 예외적 문장보다 단원의 핵심 학습 요소를 측정하는가
5. 명확성: 하나의 합리적 정답 범위가 정의되는가
6. 판별력: 단순 문장 복사가 아니라 이해·적용·판단을 요구하는가
7. 문체 중립성: 특정 생성 모델의 반복적 표현이 남지 않았는가
8. 중복성: 기존 문항과 의미·구조가 과도하게 겹치지 않는가
9. 채점 가능성: 원자적 루브릭과 허용/금지 답안이 작성 가능한가

### Gemini 생성 편향 통제

- Gemini는 초안 생성기로만 사용한다.
- 생성 모델 이름은 검수 화면에서 확인하되 최종 평가 입력에는 포함하지 않는다.
- 사람 검수자가 문장 구조를 수정할 수 있게 한다.
- 템플릿 작성 문항과 사람이 직접 작성한 문항을 섞는다.
- 동일 어구·구문 패턴의 반복 빈도를 검사한다.
- 평가 모델로 Gemini를 사용하더라도 생성 근거를 보지 못하게 하고 모델 식별자를 숨긴다.
- 가능하면 사람 채점 표본에서 Gemini 생성 문항과 비-Gemini 문항의 모델별 점수 차이를 별도 점검한다.

## 7. 채점 설계

### 7.1 객관식

- 파싱 전 원문을 보존한다.
- 정규식과 선택지 텍스트 매칭으로 최종 선택지를 추출한다.
- 복수 선택, 무응답, 상충 답변을 명시적 상태로 분류한다.
- 정확도와 함께 파싱 실패율을 별도 보고한다.

### 7.2 단답형

- Unicode 정규화, 공백·문장부호 정리, 단위 표준화 후 exact match를 계산한다.
- 승인된 별칭·동의어 목록을 사용한다.
- 수치 문항은 허용 오차와 단위를 문항별로 저장한다.
- 규칙으로 확정할 수 없는 경우에만 루브릭 평가기로 넘긴다.

### 7.3 서술형과 설명형

한 개의 모호한 1~5점 평가보다 원자적 기준을 사용한다.

예시:

```json
{
  "rubric_items": [
    {"id": "concept", "weight": 0.30, "criterion": "핵심 개념을 정확히 정의한다"},
    {"id": "causality", "weight": 0.25, "criterion": "원인과 결과의 연결을 설명한다"},
    {"id": "evidence", "weight": 0.20, "criterion": "제공된 교과서 근거와 모순되지 않는다"},
    {"id": "grade_fit", "weight": 0.15, "criterion": "지정 학년 범위의 용어로 설명한다"},
    {"id": "misconception", "weight": 0.10, "criterion": "금지된 오개념을 포함하지 않는다"}
  ]
}
```

각 항목은 가능하면 `충족/부분충족/불충족/판정불가`로 판단하고 근거 문장을 함께 반환한다. 전체 점수는 원자 항목에서 계산한다.

### 7.4 근거성 채점

RAGAS, ARES, RAGChecker의 공통 교훈은 검색과 생성을 분리하고 긴 답변을 주장 단위로 보아야 한다는 것이다.

- context relevance: 제공된 청크가 질문 답변에 필요한가
- answer faithfulness: 답변의 각 주장이 제공 청크로 지지되는가
- answer relevance: 답변이 질문에 직접 답하는가
- completeness: 모범 답안의 필수 주장을 얼마나 포함하는가
- hallucination: 근거와 모순되거나 근거 없이 추가된 사실 주장 비율
- self-knowledge leakage: grounded 문항에서 교과서 밖 지식을 필수 근거처럼 추가하는가

RAGChecker는 답변 전체를 한 점수로 보지 않고 주장별 정확·오류·누락을 구분하는 것이 중요하다고 보고한다. EduBench도 자동 평가기의 출력에 주장 목록과 각 주장 판정을 저장해야 한다.

### 7.5 LLM 심판 사용 원칙

- 모델 이름과 제공사를 숨긴 블라인드 ID를 사용한다.
- 절대 루브릭 채점을 기본으로 한다.
- EXAONE 대 타 모델의 직접 비교는 보조 분석으로만 사용한다.
- 쌍대 비교를 사용할 때는 답변 순서를 뒤집어 두 번 평가하고 불일치를 기록한다.
- 심판 모델의 원문 판단과 구조화된 점수를 모두 저장한다.
- 심판 모델과 버전, 프롬프트, 온도, 루브릭 버전을 고정한다.
- 사람 채점 표본으로 자동 채점기의 정확도·일치도를 보정한다.

LLM 심판의 위치 편향은 대규모 실험에서 확인되었다. 따라서 단 한 번의 A/B 순서 비교로 우열을 주장하면 안 된다.

### 7.6 사람 채점 표본

초기 500문항 실행에서는 다음을 권장한다.

- 서술 응답의 최소 10%, 가능하면 20%를 이중 블라인드 사람 채점한다.
- 과목·학년·난이도·모델별로 층화 표집한다.
- 두 평가자의 불일치는 합의 절차로 해결하되 원래 점수도 보존한다.
- 자동 심판과 사람의 일치도, 평균 편향, 모델별 과대/과소평가를 보고한다.
- 일치도가 낮은 루브릭은 전체 자동평가에서 제외하거나 `참고 지표`로 표시한다.

SciEx는 자유서술 시험에서 전문가 채점을 기준으로 LLM 채점의 상관을 검증했다. ARES도 적은 수의 사람 주석이 자동평가 보정에 필요함을 보여준다. 자동 평가만으로 완결된 신뢰성을 주장해서는 안 된다.

## 8. 공정한 모델 실행 프로토콜

### 8.1 기본 통제

- 모든 모델에 동일한 문항 텍스트와 동일한 근거 패킷을 제공한다.
- 도구 사용, 웹 검색, 제공사 파일 검색은 비활성화한다.
- 공통 시스템 프롬프트의 의미를 동일하게 유지한다.
- 최대 응답 길이를 공통 상한으로 맞춘다.
- 가능하면 결정적 설정을 사용하되 제공사별 지원 차이를 기록한다.
- 모델별 권장 설정을 사용하는 실험은 `native_optimized` 보조 트랙으로 분리하고 주 결과와 섞지 않는다.
- 모델 ID 별칭뿐 아니라 실제 반환된 모델 버전 또는 응답 메타데이터를 저장한다.

### 8.2 실행 순서

3,000회를 한 모델씩 순차 실행하면 시간대별 제공사 부하가 모델과 혼동될 수 있다.

- 문항 순서는 데이터셋에서 고정한다.
- 실제 호출 큐는 모델과 문항을 교차 배치한다.
- 실행 시각과 재시도 횟수를 저장한다.
- 동일 오류 정책과 최대 재시도 횟수를 적용한다.
- rate limit은 실패가 아니라 `retry_wait` 상태로 분리한다.

### 8.3 API Batch를 주 실행 방식으로 쓰지 않는 이유

OpenAI, Gemini, Anthropic은 대량 비동기 Batch API를 제공하지만, 제공사별 지원 기능·완료 시간·취소 방식이 다르다. EduBench의 일시정지·재개·문항별 재실행·실시간 로그 요구와도 맞지 않는다.

따라서 주 벤치마크는 내부 영속 큐에서 개별 API 호출을 제어한다. 제공사 Batch API는 향후 비용 절감용 별도 실행 모드로만 고려한다.

### 8.4 반복 실행

생성형 모델은 같은 입력에도 결과가 달라질 수 있다. 500×6 단일 실행은 비용과 범위 면에서 합리적인 1차 비교지만 확률적 안정성을 완전히 보여주지는 못한다.

- 기본 실행은 문항·모델당 1회다.
- 민감 문항 또는 차이가 작은 모델 쌍에 대해 선택적 반복 실행 기능을 둔다.
- 반복 결과는 평균만 내지 않고 문항별 분산과 일관성으로 표시한다.

## 9. 통계와 결과 보고

### 9.1 필수 보고값

- 유효 표본 수 `n`
- 평균 또는 비율
- 95% 신뢰구간
- 모델 간 절대 차이와 상대 차이
- 실패·무응답·파싱 실패 수
- 문항 유형, 과목, 학년, 난이도별 하위 결과

### 9.2 권장 계산

- 정확도·루브릭 평균: 문항 단위 paired bootstrap 95% 신뢰구간
- 두 모델의 객관식 차이: 문항 쌍을 유지한 차이 분포와 McNemar 검정 보조 제공
- 다중 비교: Holm 방식으로 보정한 p-value를 선택적으로 제공
- 효과크기: 점수 차이와 함께 표준화 효과크기를 제공하되 해석을 과장하지 않음
- 사람-자동 평가 일치: 가중 Cohen's kappa 또는 순위/연속 점수 상관, 평균 편향

lm-evaluation-harness도 bootstrap으로 표준오차를 계산하는 옵션을 제공한다. EduBench는 단순 리더보드 순위보다 불확실성을 전면에 보여줘야 한다.

### 9.3 종합점수

종합점수는 사용자가 설정한 가중치로 계산할 수 있지만 다음 원칙을 지킨다.

- 기본 가중치를 문서화한다.
- 원 지표를 항상 함께 표시한다.
- 가중치 변경 시 순위가 어떻게 바뀌는지 민감도 분석을 제공한다.
- EXAONE에 유리한 사후 가중치 조정을 기본 결과로 저장하지 않는다.
- 사전에 확정한 `primary_metric_profile`을 실행 후 수정할 수 없게 버전 고정한다.

### 9.4 EXAONE 분석 표현

허용되는 결론 예:

- “EXAONE은 이 데이터셋에서 학년 수준 적합성 점수가 가장 높았으며 95% 신뢰구간은 …이다.”
- “전체 정확도 차이는 불확실하지만 교과서 용어 사용과 범위 이탈률에서 일관된 차이가 관찰됐다.”
- “과학에서는 강점이 있으나 수학 계산 문항에서는 다른 모델보다 낮았다.”

피해야 할 결론 예:

- 통계적 불확실성 없이 “최고 모델”이라고 단정
- 일부 하위 집단만 골라 전체 우위로 표현
- 실패 응답을 임의로 제외
- 실행 후 가중치를 바꿔 EXAONE 순위를 올림

## 10. 데이터 오염과 문항 비공개

공개 시험 문항은 모델 학습 데이터에 포함되었을 가능성이 있다. 국내 교과서 기반으로 새 문항을 생성하는 방식은 이 위험을 줄이지만 완전히 제거하지는 않는다.

- 교과서 문장을 그대로 묻지 않는다.
- 개념 적용, 오류 교정, 복수 근거 통합 문항을 포함한다.
- 최종 데이터셋은 평가 전 외부 공개를 제한한다.
- 데이터셋 버전과 공개 상태를 기록한다.
- 공개 후에는 새 버전의 문항을 추가해 장기간 고정 벤치마크 과적합을 줄인다.
- 기존 문항의 단순 표현 변경이 오염 저항성을 보장한다고 주장하지 않는다.

출처: https://arxiv.org/abs/2502.17521

## 11. 결과 분석 화면에 필요한 기능

결과 분석이 가장 중요한 페이지라는 현재 요구를 기준으로 다음 구성이 필요하다.

### 전체 요약

- 모델별 다축 점수와 95% 신뢰구간
- 정확도, 근거 충실도, 교육과정 정합성, 학년 적합성, 환각률, 비용, 응답시간
- 종합점수보다 개별 지표를 먼저 노출

### 층별 분석

- 과목, 학년, 단원, 주 능력, 응답 형식, 난이도, 인지 수준
- 필터 적용 후 표본 수가 작으면 경고
- 최소 표본 수 미만의 순위 숨김 옵션

### 직접 비교

- EXAONE 대 선택 모델의 문항별 승/무/패
- paired 차이와 신뢰구간
- EXAONE 우세 사례뿐 아니라 열세 사례도 같은 방식으로 표시

### 오류 분석

- 환각, 범위 이탈, 오개념, 핵심 개념 누락, 응답 형식 실패
- 근거 청크와 모델 답변을 나란히 표시
- 평가 모델 판정과 사람 판정을 함께 표시

### 내보내기

- PDF: 소개 자료에 삽입할 수 있는 차트·표와 방법론 요약
- CSV: 문항별 원자료와 집계표
- JSON: 실행·프롬프트·모델·채점 버전을 포함한 재현 패키지

## 12. 권장 품질 게이트

### 데이터셋 확정 전

- 승인 문항 500개
- 모든 문항에 근거 청크와 원자적 루브릭 존재
- 주 분류 합계와 층별 분포 검증
- 정답 선택지 위치 균형
- 의미 중복 검사
- 근거 없는 정답 문항 0개
- 특정 모델을 암시하는 문구 0개

### 공식 실행 전

- 각 제공사에 3~5개 smoke 문항을 실행해 응답 파싱만 검증
- 프롬프트·모델·채점 프로필 버전 고정
- 비용 예상치 기록
- 데이터베이스 백업
- 공식 실행은 새 run으로 생성하고 중간 설정 변경 금지

### 보고서 확정 전

- 실패율과 제외 규칙 공개
- 모든 주 지표에 표본 수와 신뢰구간 존재
- 사람 채점 표본과 자동 채점 일치도 기록
- EXAONE 우세·열세 사례 모두 검토
- 방법론·제약·재실행 조건 포함

## 13. 구현에 직접 반영할 설계 결정

1. `Task = dataset item + prompt profile + scoring profile`로 분리한다.
2. 모델 제공사는 공통 어댑터 인터페이스 뒤에 둔다.
3. 원본 요청·응답과 정규화 응답을 모두 저장한다.
4. 문항에는 단일 정답 문자열뿐 아니라 원자적 루브릭과 금지 오개념을 저장한다.
5. 문항 생성 검색과 최종 모델 평가 입력의 근거 패킷을 구분한다.
6. 검색 품질과 답변 품질을 별도 지표로 저장한다.
7. LLM 심판은 블라인드 절대평가, 사람 표본 보정을 기본으로 한다.
8. 결과 분석은 다축 지표와 paired 비교를 중심으로 한다.
9. 공식 실행 후 설정 변경은 기존 run을 수정하지 않고 새 run으로 만든다.
10. 인증·사용자 권한은 로컬 단독 운영 범위에서 구현하지 않는다.

## 14. 남은 핵심 결정

구현 설계 전에 다음 한 가지를 확정해야 한다.

- 500개 문항 중 모델에게 교과서 근거 패킷을 제공하는 `grounded` 문항과 질문만 제공하는 `closed_book` 문항의 비율

이 비율은 EduBench가 “모델 자체의 국내 교육 지식”을 주로 측정할지, “교과서 RAG 학습 서비스에서의 실제 적합성”을 주로 측정할지를 결정한다.
